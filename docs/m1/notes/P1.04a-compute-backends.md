- **Status:** In review
- **Branch:** `m1/p1.04a-compute-backends`
- **Spec:** [phases.md](../phases.md#p104a-compute-backends)
- **Size:** estimated 1,340 (code 760 · tests 400 · examples 100 · docs-as-code 60 · glue 20) → **measured 1,349** (code 785 · tests 448 · examples 51 · docs-as-code 65 · glue 0), **×1.01**. P1.04 was estimated at 2,670, and split by the owner.

## Summary

Tetera can now compute on the CPU or on CUDA, chosen at run time, and it always says why. The CPU is the reference and the fallback. CUDA's libraries load at run time, so the workspace builds without the toolkit, and a machine without a driver falls back instead of failing.

Frame pools can live in pinned memory. The features Tetera plans to use were tried on this GPU under WSL2, and all five work. The gate's CUDA step now lints, tests and smokes the CUDA code with its feature on.

## How to try it

```bash
cargo run -p tetera-compute --example compute_info --features cuda
cargo run -p tetera-compute --example compute_info
TETERA_FORCE_CPU=1 cargo run -p tetera-compute --example compute_info --features cuda
TETERA_CUDA=1 cargo test -p tetera-compute --features cuda -- --nocapture
```

**The first IPC probe failed,** with `CUDA_ERROR_INVALID_VALUE`, and looked like a WSL2 limit. It wasn't. `cudarc` allocates from a stream-ordered pool (`malloc_async`), whose memory never has an IPC handle, on any system. With `cuMemAlloc`, the handle is made. ADR-0009 records this for M2's Python workers.

## Design notes and deviations from the plan

- **Every library is checked to load before `cudarc` touches it:** `cudarc` panics when a library won't load, which would turn a missing driver into a crash.
- **Pinned memory is portable and cached,** not `cudarc`'s default write-combined, which is slow for CPU reads. A pinned buffer reads through the pointer taken at allocation. Frames are uploaded only once frozen, so nothing writes to memory that is being read.
- **`cudarc` 0.19 deprecated `memcpy_stod` and `memcpy_dtov`;** the code uses `clone_htod` and `clone_dtoh`.
- **The gate's G1c was extended** in this phase, as noted above.
- **`DeviceInfo` reports the driver's CUDA version,** not the toolkit's: the toolkit can differ per machine, and `compute_info`'s libraries show which one loaded.

## Tests, and the mutants

- **37 tests in `tetera-compute`:** 14 in every build, 9 more with the `cuda` feature, of which 7 run on the GPU with `TETERA_CUDA=1`. Plus the gate's tests in xtask, updated for its CUDA steps.
  - **Selection,** over faked machines: forced, unbuilt, no driver, no device, several devices.
  - **The fallback:** a chosen device that won't start; a missing library as an error, not a panic.
  - **On the GPU:**
    - the device's description;
    - buffers round-tripping, a million samples, and an empty buffer;
    - pinned buffers aligned, zeroed and writable;
    - a pool of four full frames in pinned memory, uploaded and read back;
    - the feature check's exact findings.
- **Broken on purpose:** the fallback to the CPU when the driver is missing. Its mutants in `select` and `Compute::start_cuda` are caught.
- **Mutants:**
  - run twice, since the CUDA code compiles only with its feature: with `--features cuda` and `TETERA_CUDA=1` on the GPU, and without the feature on the code both builds share;
  - the first run **missed 22**: weak tests of the feature check and the version arithmetic, an empty buffer never made, and code only the other build compiles. Tests were added, and `cuda_version` became a function of its own;
  - now: **104 tested with CUDA, 63 caught, 39 unviable, and 2 missed that only the other build compiles; 42 without, with the 19 missed being code only the CUDA build compiles.** Read together, nothing testable is missed;
  - three more are excluded in `.cargo/mutants.toml`, each with its reason: the readers of `TETERA_CUDA` and `TETERA_FORCE_CPU`, and `synchronize`, whose effect P1.04b's kernels will make visible;
  - the gate's new steps: **34 tested, 28 caught, 6 unviable.**

## Follow-ups and known gaps

- **The checkpoint's `--mutants` step** builds one way, so code behind a `cuda` feature shows as missed. It should run both ways and count only what both miss. This needs doing before P1.12's checkpoint.
- **`synchronize`'s mutant exclusion** is lifted in P1.04b, once kernels make asynchronous work observable.
- **An IPC handle opened from another process,** when M2's Python workers need it.
- **The service under systemd** won't read `~/.profile`: P1.13's unit must set CUDA's library path itself.
