## Summary

The workspace every later phase lands in, and the local gates that decide whether a phase is ready: `cargo xtask layering`, `cargo xtask gate quick|phase|checkpoint|milestone` and `cargo xtask doctor`. Also the docs skeleton, ADRs 0001–0005, the working rules in `CLAUDE.md`, the toolchain guide, shared VS Code settings and the pull request template.

## What was built

- **The workspace:** resolver 3, edition 2024, Rust 1.98.1 pinned (teta-wot's), workspace lints forbidding unsafe code and warning on missing docs, mold through clang, dependencies optimised in dev and test builds, `deny.toml`, `.gitattributes` (LF), `rustfmt.toml`.
- **`tetera-core`:** nearly empty, with `VERSION`, `name_and_version()` and the `hello` example, so the gates and the debugger have a crate.
- **`xtask`**, with no dependencies beyond serde and serde_json:
  - `metadata`: the parts of `cargo metadata` the tasks read;
  - `layering`: the layer table of plan §6.2 with every planned crate, the allowed edges within a layer, and the rules of ADR-0005;
  - `reach`: the changed files since the merge base, committed or not, and what they reach;
  - `gate`: the steps each level runs, and why;
  - `runner`: runs the steps, the fresh clone, and the summary;
  - `stress`: test binaries side by side, each run pinned to two CPUs with `taskset`;
  - `doctor`: tools, disk, memory, git, location;
  - `toml_lite`: just enough TOML to read manifests' lints;
  - `exec`, `cli`.
- **`.cargo/mutants.toml`:** the 11 mutants no test can tell apart, each with its reason.
- **Docs:** `docs/README.md`, `docs/goal.md` (moved from `tetera.md`), the ADR index and template, ADRs 0001–0005, the notes' index (with each phase's status) and template, `docs/m1/manual-tests.md`, `docs/setup/toolchain.md`, `CLAUDE.md`, a new root `README.md`.
- **`.vscode/`** (launch configurations for CodeLLDB, recommended extensions, rust-analyzer on clippy) and `.github/pull_request_template.md`.

## Ideas taken from OScope

From its documents, in our own words (ADR-0002):

- the layer table checked against `cargo metadata`, with named edges allowed within a layer, and the unsafe crates setting their own lints (OScope ADR-0005);
- local gates as the merge gate (OScope ADR-0038), running only what a change reaches (OScope ADR-0061);
- test suites side by side on two CPUs each (OScope's `two-core` runs);
- estimates in parts, committed before the code, and mutation checks read against the tests (both retrospectives).

## How to try it

From a clone in WSL (`docs/setup/toolchain.md`):

```bash
cargo xtask doctor
cargo xtask layering
cargo xtask gate quick
cargo xtask gate phase
cargo xtask gate checkpoint --mutants
cargo run -p tetera-core --example hello -- --smoke
```

Each gate prints its steps and ends with `summary: target/gates/<time>-<level>/summary.md`. [crates/tetera-core/README.md](../../../crates/tetera-core/README.md) says how to debug the example from VS Code.

## Design notes and deviations from the plan

- **`examples/*` isn't a workspace member yet.** Cargo refuses a member pattern that matches no folder. It joins with the first whole-server example crate.
- **Dependency optimisation is in `Cargo.toml`'s profile,** not `.cargo/config.toml` as the spec said: the same effect, in the conventional place.
- **`tetera-log` is in the layer table** (L1), as the plan's change for P1.02 says, but not created: P1.02 creates it.
- **The fresh clone keeps its target folder inside the clone** (`target/gate-clone/src/target`, kept by `git clean -e /target/`), not in `CARGO_TARGET_DIR`. Tests that start cargo would inherit that variable and wait on the lock held by the `cargo test` running them. The first design had this flaw; the end-to-end tests showed it before it bit.
- **The mutants step runs 4 at a time** (`--jobs 4`): one at a time would take far longer as xtask's end-to-end tests grew.
- **Stress labels name the target's kind:** a library and a binary often share a name, and the first run's log showed `xtask/xtask` twice, one of them a binary with no tests.
- **`deny.toml` allows unused licences silently** (`unused-allowed-license = "allow"`): the list is policy, not an inventory.
- **`cargo-mutants` and `taskset` are required by the doctor:** the checkpoint and phase gates need them.
- **The doctor's thresholds:** 40 GB of free disk for G2 (warn below), 8 GB of memory (warn below), and `CARGO_BUILD_JOBS` suggested at 1.5 GB a job.

## Tests, and the mutants

- **72 tests:** xtask's 60 unit tests and 11 integration tests, and tetera-core's one.
  - **Layering:** synthetic crates for each rule, and two real scratch workspaces: one with an upward edge, and one with a path dependency outside the workspace.
  - **Reach:** synthetic graphs, and a real git repository with committed, unstaged and untracked changes.
  - **The gate end to end:** a scratch workspace whose quick gate must pass, naming only the changed package; one with a failing test and an upward edge, whose quick gate must fail on exactly those two steps; the stress step on a passing, a failing and an unbuildable crate.
  - **The binary:** exit codes 0, 1 and 2, the doctor's report, and the doctor failing with an empty `PATH`.
- **Broken on purpose:** an upward edge and missing lints, in the real workspace (above); a failing test and an upward edge in a scratch workspace, in the tests.
- **Mutants:**
  - first, reach and layering only, as the spec asks: 12 of 60 missed: build-dependencies, an edge to an unplaced crate, Rust lints alone, `check_workspace` against a broken workspace, and `changed_files` entirely. Tests added; 59 of 59 viable caught;
  - then the checkpoint's first run with `--mutants` covered all of xtask: **81 missed**, many in the gate's own verdicts (whether a step failed, whether a stress run passed). The end-to-end tests above came from that run;
  - now: **286 tested, 234 caught, 52 unviable, none missed.** The 11 excluded in `.cargo/mutants.toml` are a time limit's `>` against `>=`, the condition that decides whether a checkpoint computes a merge base for `--mutants`, and `fresh_clone`, which needs a clone of this very workspace and runs for real in every checkpoint.

The estimate counted the gate's logic but not how much testing a gate needs before its verdicts can be trusted: the tests are 38 % of the phase. OScope's P02 overran by ×2.15 for the same reasons, doc comments and formatting. For the next phases' estimates: count doc comments and rustfmt's line breaks in the code, and allow tests of at least the code's size for anything that decides or detects.
