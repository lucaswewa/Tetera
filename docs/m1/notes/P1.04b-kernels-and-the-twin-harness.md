# P1.04b: Kernels and the twin harness

- **Status:** In review
- **Branch:** `m1/p1.04b-kernels-and-the-twin-harness`
- **Spec:** [phases.md](../phases.md#p104b-kernels-and-the-twin-harness)
- **Size:** estimated 1,420 (code 625 · tests 650 · examples 100 · docs-as-code 25 · glue 20) → **measured 1,405** (code 780 · tests 507 · examples 95 · docs-as-code 14 · glue 9), **×0.99**

## Summary

Tetera can now build CUDA kernels, load them, launch them, and prove that each computes what its CPU twin computes. The first pair, scale and offset from 16-bit samples to floats, agrees bit for bit over a full frame. It does so whether the kernel came from `nvcc`'s fat binary at build time or from NVRTC at run time.

The GPU's memory is shared out as budgets, and a request beyond a budget is refused. The workspace still builds without the CUDA toolkit.

Two lessons from OScope's notes changed the plan:
- **Kernels are built as fat binaries,** not PTX alone, which a driver older than the toolkit refuses.
- **Copies with pinned memory now wait until they are done.** A test showed P1.04a's `upload` and `download_into` returning before the GPU had read or written pinned memory, every time.

## What was built

- **The kernel build,** `crates/tetera-compute/build.rs`:
  - with the `cuda` feature and `nvcc` found, each `kernels/*.cu` becomes a fat binary (`-arch=all-major`): cubins for compute capabilities 7.5, 8.0, 9.0, 10.0, 11.0 and 12.0, and PTX for 12.0;
  - a kernel `nvcc` refuses fails the build;
  - `NVCC` names `nvcc`, and `NVCC=none` skips it;
  - each kernel's source, and its fat binary when there is one, are embedded through a generated `kernels.rs`.
- **`kernels`,** with the `cuda` feature: `KernelSource`, `SCALE`, and `Module`, loaded from the fat binary or through NVRTC, which says which (`Origin`).
- **`CudaBackend`** gains:
  - `module`, which loads each module once and shares it with clones;
  - `time_ms`, which times work on the device between two events;
  - copies that return once done: `upload` once it has read the host's memory, `download_into` once it has written it.
- **`ops`:**
  - `scale_offset_cpu`, the twin, in chunks over the CPU's pool;
  - `CudaBackend::scale_offset`, the kernel;
  - `scale_offset`, on whichever backend `Compute` chose.
- **`twin`:** `Tolerance`, `compare`, `Comparison` and `Worst`; `gpu_for_tests` and `cuda_or_skip!()`.
- **`budget`:** `VramBudgets`, `Budget`, `Grant` and `AccountReport`.
- **The `twin_scale` example,** and ADR-0010.
- **The plan's §6.6** now says fat binary, not PTX.
- **No new dependencies.**

## Ideas taken from OScope

From its documents, in our own words (ADR-0002):
- **a fat binary built with `-arch=all-major`:** its P07 notes record PTX from CUDA 13.4 refused by a driver that ran 13.2;
- **copies from pinned memory that wait:** its P07 notes record an upload returning before the copy, and the test that overwrites the source at once, which Tetera's test follows;
- **twins compared exactly** where both sides compute in the same order (its P07 notes).

VRAM budgets are Tetera's own, from its plan's R3: OScope's documents don't mention them.

## Performance

Scale and offset over a full frame, 5,472 × 3,648 (19,961,856 samples), from `twin_scale` in release: the CPU and the kernel the best of 10, each copy once.

| | Time |
|---|---|
| CPU, 16 threads | 5.70 ms |
| CUDA kernel | 0.35 ms |
| Upload, 38 MiB from pageable memory | 22.2 ms |
| Download, 76 MiB to pageable memory | 36.1 ms |

The kernel is about 16 times faster than the CPU, but the copies dwarf both. Pipelines must keep frames on the device between steps, and copy from pinned memory (P1.04a's `PinnedAllocator`), as plan §6.6 says.

## Design notes and deviations from the plan

- **A fat binary, not PTX:**
  - **why:** a driver refuses PTX from a toolkit newer than itself, and the instrument PC's driver isn't known. Cubins from any CUDA 13 toolkit run on any CUDA 13 driver;
  - **what it costs:** 29 KiB for scale and offset, six cubins and the PTX;
  - **the plan:** §6.6 and this phase's spec said PTX. §6.6 is updated; ADR-0010 gives the alternatives.
- **Copies wait for themselves,** a fix to P1.04a:
  - **what failed:** a new test filled 64 MiB of pinned memory, uploaded it, and changed its last byte at once. The GPU's copy held the changed byte. Downloading into pinned memory, the last byte was still zero when the call returned;
  - **why:** `cudarc` waits for nothing when copying from or to a plain slice. The driver waits for pageable memory, not for pinned;
  - **the fix:** `upload` and `download_into` synchronize the stream. Overlapping copies with work, holding the frame until an event says the copy is done, waits for the preview pipeline (P1.14a).
- **Both sides fuse the multiply and the add explicitly:** `fmaf` in the kernel, `mul_add` in the twin. CUDA's compilers fuse on their own by default, and Rust never does, so leaving it to them would differ in the last bit. Written out, the twins are held to `Tolerance::EXACT`. A test shows the CPU's result differs from the unfused one.
- **`NVCC`, when set, is the only `nvcc` tried.** Without that, a machine with CUDA in its usual place couldn't test the NVRTC path: `NVCC=none` forces it.
- **`CudaBackend::time_ms`** wasn't in the spec. `twin_scale` needs kernel times, and later benchmarks will too.
- **Budgets are bookkeeping:** a user takes a grant before allocating, and nothing yet stops an allocation without one. Tying device allocations to grants waits for the pipeline engine (P1.08), which allocates on its users' behalf.
- **An infinity matched anything under a relative tolerance:** half of an infinite expected value is infinite. The mutants pointed at `Tolerance::allows`; a NaN or an infinity now matches only itself, whatever the tolerance.
- **A launch is refused beyond `u32::MAX` elements,** the kernel's index type: about 215 full frames, so no frame comes near it.

## Tests, and the mutants

- **28 new tests in `tetera-compute`:** 17 in every build, and 11 more with the `cuda` feature, all on the GPU with `TETERA_CUDA=1`. The crate now has 31 tests without the feature, and 51 with it.
  - **The harness:**
    - tolerances adding their absolute and relative parts;
    - NaN and infinity matching only themselves, under absolute and relative tolerances;
    - the worst difference located, even within the tolerance, and a NaN counted as the worst;
    - results of different lengths refused;
    - with `TETERA_CUDA=1`, CUDA tests really getting a GPU, so none can skip unseen.
  - **Budgets:**
    - the capacity shared out, and no more;
    - one budget per user;
    - an allocation beyond a budget refused as `Busy`;
    - a released budget held while its grants live;
    - the share kept free;
    - eight threads granting at once, never past the limit.
  - **The twin:** values checked by hand; the fused rounding; work over several chunks; the chosen backend doing the work.
  - **On the GPU:**
    - the kernel and its twin bit for bit at 1, 255, 256, 257 and 1,000,003 samples and a full frame, either side of the block size;
    - mismatched buffers refused, and an empty one launching nothing;
    - modules loaded from the fat binary and through NVRTC; a kernel that won't compile, and a module that won't load, refused; a module loaded once and shared with clones;
    - copies with pinned memory done when they return;
    - `synchronize` waiting for 50 queued kernels, checked with an event;
    - `time_ms` timing an upload, and passing its work's error through.
  - **Both kernel paths:** every CUDA test passed with `nvcc`'s fat binary, and again built with `NVCC=none`, through NVRTC.
- **Broken on purpose:** the harness's comparison. A result out of tolerance must fail it, and the mutants in `compare` and `Tolerance::allows` are caught.
- **Mutants:**

  - run twice, as in P1.04a: with `--features cuda` and `TETERA_CUDA=1` on the GPU, and without the feature, on the code both builds share;
  - the first run **missed 7 with CUDA:**
    - `||` for `&&` in `Tolerance::allows`, which led to the infinity bug above;
    - `||` for `&&` in `compare`: no test had a NaN after a finite difference;
    - `gpu_for_tests` giving `None`, or inverted: every CUDA test could have skipped unseen;
    - the CPU's chunk size, `64 * 1024` as `64 + 1024`: only the speed changes. It is written `65_536` now, leaving nothing to mutate;
    - and 2 that only the other build compiles.

    Tests were added for the first three;
  - now: **208 tested with CUDA, 151 caught, 55 unviable, and 2 missed that only the other build compiles,** the non-CUDA `start_cuda` and `cuda_built`, which is constant in each build. **Without the feature, 208: 91 caught, 22 unviable, and the 95 missed all code only the CUDA build compiles.** Read together, nothing testable is missed;
  - **`synchronize`'s exclusion is lifted,** as P1.04a planned: its mutant is caught, by the event test and by the pinned copies, which now wait through it.
